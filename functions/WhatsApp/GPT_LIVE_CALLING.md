# In-app GPT-Live calls

The in-app voice transport uses `gpt-live-1` with WebRTC and client delegation. Phone and WhatsApp calls continue through their existing Realtime controller.

`assistantBrowserCall.js` creates a Live session with `store: false`, validates the caller/topic, freezes the voice price, and queues the existing `runWhatsAppRealtimeCall` worker. That worker dispatches Live sessions to `assistantLiveController.js`. The microphone stays disabled until the session starts and the server controller acknowledges readiness.

Each substantive request uses the current assistant's configured model, reasoning effort, instructions, conversation history, permissions and native tool implementations through the shared chat helpers. OpenAI and OpenRouter model routing are shared with chat. Voice has no separate backend model setting. Each model round uses the same token estimate and model-specific Gold divisor as chat. Tool fees still apply through the normal tool implementations.

## Pricing

- Voice: **40 Gold/minute**, calculated from cumulative provider seconds and rounded up to whole Gold.
- Minimum: **15 seconds / 10 Gold**, credited toward total connected time. Silence and muted time count.
- Assistant: its normal configured model rate, plus applicable tool charges.
- The user confirmed **10,000 Gold = EUR 49** on 2026-09-11. Thus voice alone costs EUR 0.196/min retail; provider voice pricing is USD 0.05/min plus backend inference.

Cumulative usage updates and final usage reconcile transactionally with the Gold ledger. Backend rounds have independent deduplication markers. No negative balance is created. Rates are frozen per session/model round. The UI and server share `assistantLivePricing.js`. The owner-only usage summary distinguishes final cost from usage so far when final provider usage is unavailable.

## Transcript and interruption handling

Provider deltas retain their original whitespace/timing in the session's `liveTranscriptFragments` subcollection. Stable display groups update comments without treating each fragment as another chat message. Full backend results are stored separately from spoken transcripts, so returned links remain available in chat even when speech is shortened. No audio recording is added.

Delegation events carry an ID and offset, not a task prompt. The controller waits for transcript context and a short coalescing window; that window is not proof the caller finished speaking. New input invalidates stale execution before tools and subsequent model rounds. Spoken requests use the same tool permissions as chat, with no extra voice-only confirmation gate. Underlying tool approvals and essential clarification questions still apply. Tool outcomes are saved before another delegation runs; uncertain actions require state verification before retrying.

After a sideband disconnect, missing speech cannot safely be reconstructed. Reattachment only closes and settles the session. Hangup keeps the event receiver open until `session.closed` or a bounded timeout. The existing browser/iOS/Android microphone and background lifecycle remains in place.

## Grounded spoken status

`assistantLiveStatus.js` requires an actual failure signal (a tool failure flag, HTTP error status or thrown exception) and a specific sanitized cause/code before creating a spoken error. Successful or empty search results, text mentioning errors, waiting for input/authentication, cancellation and newer speech are not technical failures. Missing details produce an unconfirmed outcome, never an invented diagnosis. `liveToolResults.outcome` stores this separately from `status: completed`, which only means the tool execution returned.

Progress is typed application data, not arbitrary prose. The Live interface receives an `application_status` envelope and may describe only its step, active work and confirmed cause. Silent `application_error_state` updates carry error evidence only; successful retries clear it before final answer delivery. Background jobs have separate scopes. Neither these updates nor a missing acknowledgment cause answer replay. Spoken error claims in the transcript do not constitute evidence for the backend; it must verify the execution records and must not invent an explanation such as a display bug. A superseded request's late failure is recorded without interrupting the new request.

Contact note pages identify the contact in their URL. The backend resolves `contact.noteId`, verifies project membership and both objects' visibility, and includes only that verified reference in its context. If a note read mistakenly uses the current contact ID, it resolves the link again immediately before execution and records both requested and effective arguments. Explicit targets in other notes/projects are preserved. Audited stateless read exceptions return a failed tool result to the normal assistant loop so it can correct arguments in the same delegation; unchanged failed reads may execute at most twice. Writes, revoked tool permissions, cancellation and exhausted Gold retain their stop behavior. Corrected contact aliases share progress identity with the canonical note, so successful retries clear the earlier error. Spoken status errors are deduplicated by request/job scope and cause, including the tool-to-backend-abort path; new requests and different causes remain reportable.

## Delivery and verification

The browser opens the last working desktop microphone and capture mode immediately (falling back to the default if it was removed), without a pre-call dialog or instruction to speak. Local warm-up and comparison start during connection setup; a separate sender clone stays muted until both the provider and controller are ready and local warm-up has completed. Warm-up overlaps signaling and is bounded to 4.5 seconds; unavailable metering does not block the call. Other available inputs are measured locally, and the single WebRTC sender switches when another input has a sustained, materially higher level. A rolling window and four-second cooldown prevent oscillation. Comparison pauses while assistant audio is playing and while the page is hidden, but the selected input's live meter keeps updating. The floating bar displays that input's name and current level, including a local-preview label before transmission starts. Phones meter only the system-selected input to preserve Bluetooth/speaker routing. Device changes are discovered during the call. All comparison captures and sender clones stop on hangup. Digital silence can trigger fresh capture without audio processing for the known Chrome/macOS issue; a suspended analyser is not treated as silence. No microphone samples leave the device except the selected call track. Startup diagnostics retain signal/selection/transmission timing and bounded levels, without device names or audio.

Readiness requires `session.started` plus the controller acknowledgement; an owner-only status read recovers a missed acknowledgement. The server's connection acknowledgement never requests speech. The browser primes playback within the initial user gesture and sends the localized opening greeting as session-wide commentary only after remote playback succeeds and the controller is ready. A blocked player exposes an explicit enable-audio button, and resuming playback does not repeat the greeting. The controller stores `greetingAcknowledgedAt` when the provider acknowledges this event; that confirms acceptance, not physical audibility.

Startup can be cancelled, duplicate starts are guarded, and late successful provider responses are closed through `endAssistantBrowserCallSecondGen`. The controller honors the owner's cancellation flag before further assistant actions and settles ongoing work before publishing final cost.

Deploy the frontend together with `startAssistantBrowserCallSecondGen`, `getAssistantBrowserCallSummarySecondGen`, `updateAssistantBrowserCallContextSecondGen`, `endAssistantBrowserCallSecondGen`, `runWhatsAppRealtimeCall`, and the existing `cleanupStaleWhatsAppCalls` scheduled function. Include their shared Functions sources. The browser uses `gpt-live-v2`; older cached clients are rejected with a refresh instruction before creating a paid session, because they cannot release the playback-gated greeting. No new secret is needed; use the configured OpenAI key with GPT-Live access. No Firestore backfill is required; existing Realtime sessions keep their original path and pricing.

`node browser-tests/voice-microphone/run.js` uses Playwright Chromium and synthetic Web Audio inputs to verify continuous stronger-input selection in both directions, pausing selection during playback, capture cleanup, and recovery from digital silence. It uses an isolated browser and localhost harness, without real microphone access or paid sessions.

Run focused Functions tests with `ci/jest.functions.config.js`, client lifecycle tests with `ci/jest.web.config.js`, and the webpack production build under Node 22. Before production rollout, perform a real call with a configured OpenAI model and an OpenRouter model; check clarification, interruption, tool results/links, hangup, Gold history and final usage. Device testing remains necessary for iOS shell background capture, iOS Safari resume and Android notification hangup.
