# AT-2709: continue existing email tasks

Automatic continuation is wired into Gmail labeling follow-ups and the explicit
Create task action for Gmail and Microsoft accounts. The existing Draft MR is
[!643](https://gitlab.com/alldonegmbh/alldone/-/merge_requests/643).

## Behavior agreed with Karsten

- Match by integration owner, provider, normalized mailbox and opaque thread ID,
  across the user's accessible projects. Keep the original task and project even
  when a later email would route elsewhere. Without a thread ID, use only the
  individual message identity; never group unrelated emails by subject.
- Reopen completed tasks. Preserve assignee, workflow, privacy, origin and approval
  metadata. Pending assistant suggestions remain suggestions; rejected assistant
  suggestions remain rejected rather than reopening an assistant-owned task for
  execution.
- Add a concise summary of each new email as a linked comment, including available
  sender/date metadata. Do not copy the full email into the comment. Informational
  follow-ups also continue existing tasks, including emails without a new label match.
- Add concrete changes to the required work to the actual task description. Preserve
  existing text, including user notes, with an additive update. Update title, explicit
  deadline and priority only when the field still equals its recorded email-generated
  baseline and the version read for summarization. Legacy tasks without a baseline
  receive additive description updates and comments; their existing fields are not
  overwritten. Assignment and reminders are not inferred from emails.
- When several tasks plausibly match, create a separate task rather than selecting
  arbitrarily. A uniquely linked message or a verified per-message registration
  resolves repeat processing of that exact email. A new message with unresolved
  thread ambiguity still receives a separate task. New automatic tasks retain
  `assistant_suggestion` origin and the existing visible explanation/approval rules.

## Persistence and workflow integration

`emailThreadTaskStore.js` uses automatic single-field indexes only. TaskService
commits the initial task, baseline and thread/message registrations together.
Creation races reuse the winning task; the ordinary feed persistence path must
never overwrite its already committed task document. Adopted tasks skip creation
feeds. Deleted registrations recover through live task lookup.

`emailThreadContinuation.js` performs lookup before summarization or task creation.
The summary model receives bounded email context and a small allowlist of optional
content changes. TaskCommentService rechecks task readability and selection inside
its transaction. Summary comment, counters, content changes, reopening, message
linkage and message registration commit together. Deterministic comment IDs and
linked-message checks make duplicate processing a no-op; concurrent emails preserve
both descriptions/comments. Older emails cannot revert newer title/deadline/priority
updates. A selection that becomes ambiguous during the model call fails for retry
rather than changing the wrong task.

Gmail continuation precedes the post-label assistant's task/topic actions. Failure
is recorded as `threadContinuationPending`; subsequent syncs explicitly fetch those
emails even after archival or history-cursor advancement, without classifying or
charging classification again. The create_task tool also uses atomic persistence,
covering races after the preflight. Reused tasks do not receive misleading new-project
routing comments. The email line uses the same continuation path for both providers
and refunds the creation charge if a concurrent request already created the task.

## Scope and limitations

- The existing automatic mailbox task workflow is Gmail labeling. Outlook uses the
  explicit Create task workflow; no new Outlook polling/labeling automation is added.
- Daily inbox overview tasks (`apis/EmailIntegration.js`) have no individual thread
  identity. The assistant's inbound instruction channel also has no verified mailbox
  thread identity. Both remain outside mailbox thread continuation.
- AI summaries/content changes depend on the configured model and available bounded
  body context; attachments are not analyzed here. No speculative assignment changes
  or automatic replacement of manually edited fields is attempted.
- Duplicate retries avoid another model call. Simultaneous requests may both invoke
  the model before one transaction wins; only the persisted continuation is charged.
  Gold billing and follower notifications happen after persistence, following the
  existing services. They are not part of the Firestore transaction, so a process
  crash in that gap can leave an unpaid operation or a missing notification.
- No live mailbox/provider smoke test, merge or deployment has been performed.
  No credentials, environment changes, migration or new composite indexes are needed.
