# AT-2709: email thread task reuse

This branch prepares the storage and comment primitives for AT-2709. **Automatic
thread reuse is not enabled yet.** The interactive product decisions below are
required before connecting these primitives to the task creation flows.

## Existing flows

- `Gmail/serverSideGmailLabelingSync.js` classifies each message and runs a follow-up
  assistant. Its `create_task` tool in `Assistant/assistantHelper.js` stores the
  Gmail message/thread metadata. These tasks are assistant suggestions and must
  retain their existing approval behavior.
- `Email/emailLine/emailLineService.js` implements the explicit Create task action
  for Gmail and Microsoft accounts. It currently reconciles individual messages
  before summarizing/charging Gold. Thread reuse must also happen before spending
  Gold, and concurrent creation must use the same atomic persistence primitive.
- `apis/EmailIntegration.js` creates daily inbox summary tasks. They have no
  individual thread identity and are outside this change.
- The assistant's inbound email channel handles explicit email instructions;
  it does not currently attach mailbox thread metadata to created tasks.

## Prepared primitives

- `emailThreadIdentity.js` keys opaque thread/message IDs by integration owner,
  provider and normalized mailbox address. Missing thread IDs fall back to a
  message identity; missing account addresses cannot match a task. Legacy Gmail
  metadata can match a proven mailbox address without a provider/owner field.
- `emailThreadTaskStore.js` finds readable matches in a supplied project scope
  using single-field indexes. It commits a new task and its thread registration
  under `users/{userId}/emailThreadTasks/{key}` together. The caller must supply a
  selection policy for pre-existing matches. Transaction retries contain no model
  calls, Gold charges or feed side effects. This module is not connected to
  `TaskService` yet.
- `TaskCommentService` accepts deterministic comment IDs and email metadata. The
  comment, task/chat counters and (optionally) linked message IDs update in one
  transaction. Retries skip existing comments and notifications. Email comments
  require matching account/thread metadata and an explicit integration owner.
- Provider message contexts now expose the thread/conversation ID, date and
  complete available body separately from the existing 4,000-character model
  context. Outlook bodies may be HTML; the comment adapter must convert them to
  plain text if full text comments are selected.
- Individual-message reconciliation includes `gmailData.messageIds` and strictly
  checks provider, mailbox and any stored integration owner.

## Product decisions awaiting Karsten

1. Which task fields should a new email update: only comment/email linkage, title
   and description, or also dates/priority/assignment?
2. Should completed tasks remain completed, reopen, or stop automatic handling?
   Which task wins if several tasks already match the thread?
3. Should comments include sender/date/subject/full available text, a summary, or
   just a summary and email link? Full text exceeding the normal 5,000-character
   comment limit needs a deduplicated multi-part adapter.
4. If the label routes a later email to another project, should the original task
   remain authoritative across accessible projects, or should reuse stay scoped
   to each project?

After clarification, wire the shared lookup/persistence into both creation paths
and the Gmail follow-up preflight (including informational messages in an existing
task thread). Add flow-level tests for the selected policy, retries, comments,
Gold billing, and unchanged origin/approval behavior. No migration, indexes or
deployment are required for these preparation changes.
