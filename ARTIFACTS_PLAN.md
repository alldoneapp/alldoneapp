# Project Artifacts Plan

Status: **Phases 0–3 built** on `claude/project-artifacts-feature-6bl3ek` (2026-10-25), not yet
merged or deployed. The product decisions are in §9, what was built and where it deviates from this
plan in §10, and what a deploy needs in §11.

Goal: every project gets an **Artifacts** section in place of the Chats tab. An artifact is a thing
the project _produced_ (a dashboard, an HTML page, a report, a PDF, a spreadsheet, an image),
either uploaded by a person or created by an assistant / VM run. The list is sorted by last edit,
each artifact opens at its own URL, and it is **rendered live** (an HTML artifact runs, it is not
downloaded), visible to exactly the people who may see it, with the same privacy model as notes.

Chats stay. They lose their slot in the five root tabs and remain reachable through the existing
top-right Chats button (`components/TopBar/ChatsButton.js`, which already opens All projects →
Chats) and the per-project sidebar entry.

---

## 1. What an artifact is (and is not)

| Kind       | Examples                                          | How it is shown                                                      |
| ---------- | ------------------------------------------------- | -------------------------------------------------------------------- |
| `web`      | dashboard, landing page, HTML report, SVG, a site | Runs in a sandboxed iframe served from the **artifact origin** (§4)  |
| `markdown` | specification, meeting report                     | Rendered by the same self-written renderer as the wiki (no raw HTML) |
| `document` | PDF                                               | Inline PDF viewer, served from the artifact origin                   |
| `media`    | image, video, audio                               | Native viewer                                                        |
| `data`     | CSV, JSON, XLSX                                   | Table preview + download                                             |
| `file`     | anything else (zip, docx, pptx, …)                | Metadata card + download                                             |

Sources, recorded on the artifact so the list can filter by them:

- `upload` — dropped into the Artifacts list, or "Save as artifact" on an attachment that already
  lives in a note, task or chat comment (explicit promote, see decision 3).
- `assistant` — an assistant called `create_artifact` / `update_artifact` (§6).
- `vm` — files a VM job wrote to `/home/user/output/` (§6).

An artifact is **not** a note: it has no collaborative Yjs editing. It changes by being replaced
with a new **version** (uploaded again, or regenerated by an assistant). That is what makes it
safe to serve and cheap to cache: a version is immutable.

## 3. Data model

Follows the existing object layout so access projection, feeds, followers, backlinks and object
chats can be reused instead of rebuilt.

```
artifacts/{projectId}/items/{artifactId}                   metadata (client-readable, rules below)
artifacts/{projectId}/items/{artifactId}/versions/{vId}    immutable version manifests (server-written)
Storage: artifacts/{projectId}/{artifactId}/{vId}/{path}   file bytes, read only by serveArtifact
```

Artifact document (mirrors `mapNoteData` where it can):

- identity & list: `title`, `extendedTitle`, `description`, `kind`, `source`, `hasStar`,
  `created`, `creatorId` (user or assistant id), `lastEditorId`, `lastEditionDate`, `views`
- content pointer: `currentVersionId`, `versionCount`, `entryPath` (`index.html` for a bundle),
  `mimeType`, `sizeBytes`, `previewText` (first ~300 chars of text kinds, for search and the row)
- privacy, exactly as notes: `userId` (owner), `isPrivate`, `isPublicFor`, plus the server-owned
  projection fields `readerIds` / `followedReaderIds` / `backlinkIdsVisibleTo`
- `serveSecret`: the random part of the artifact's web address (§4). Server-owned like the
  projection fields: set by the create trigger, rotated by the server, never written by a client
- graph: `followersIds`, `isVisibleInFollowedFor`, `linkedParent*Ids`, `parentObject` (the task,
  note or chat it was created from — so a VM-built dashboard links back to its task)
- assistant thread: `assistantId`, `isAssistantEnabled`, `commentsData` (the artifact gets its
  own chat like every other object — that chat is the iteration loop, §5)

Version manifest: `files: [{ path, size, mimeType, sha256 }]`, `entryPath`, `createdBy`,
`createdAt`, `changeSummary`, `sourceRef` (VM correlationId / assistant comment id).

Writes: metadata (title, description, privacy, star, followers) are direct client writes under
the same rules as notes. **Versions and bytes are server-only**: upload goes to a staging path via
a signed URL, and a callable `commitArtifactVersion` validates (size, type, bundle extraction),
moves the bytes into place and writes the manifest in one step. That keeps every byte that will
later be served under the server's control.

## 4. Serving

Artifacts get the same protection level as notes, plus one rule that notes do not need.

**The access level is the note level.** A note has a fixed app URL that requires sign-in and
project access, and its bytes are fetched behind that through a Firebase download-token URL
(`getNoteData` in `utils/backends/firestore.js` calls `getDownloadURL()`; note attachments work
the same way). Whoever holds such a token URL can read the file without signing in. Artifacts work
the same: the app URL (§5) is the protected, shareable address, and behind it sits a fixed web
address with a secret part:

```
https://alldone-artifacts.web.app/a/{projectId}/{artifactId}/{serveSecret}/index.html
```

That address works without sign-in, like a note attachment link. It is one step better than a
note attachment in one respect: the secret can be **rotated**. The server replaces `serveSecret`
when the artifact's privacy changes or a member leaves the project, and a "Reset link" button in
Properties does the same by hand. Old links then stop working. A note attachment's download token
can never be withdrawn.

**The one rule notes do not need: artifact HTML is never served from the app origin.** A note is
text that our own code renders. An HTML or SVG artifact is code that runs by itself, written by a
model or uploaded by someone. On `my.alldone.app` it would run with the viewer's Firebase session
(auth lives in IndexedDB on that origin) and could do anything the viewer can: read every project,
create tasks, spend Gold. That is not hypothetical, because assistants read emails: a crafted email
can steer an assistant into building a "dashboard" that carries such a script, and the colleague
who opens it runs it with their own account. Artifacts are therefore served from a **separate
site**, a second Firebase Hosting site such as `alldone-artifacts.web.app`. `web.app` is on the
Public Suffix List, so this is a different _site_ from both `alldonealeph.web.app` and
`alldone.app`; a subdomain of `alldone.app` would not be. Every response also carries
`Content-Security-Policy: sandbox allow-scripts …` **without** `allow-same-origin`, so each
artifact runs in an opaque origin and cannot read another artifact's storage either.

**Why not plain download-token URLs, then?** Because they cannot serve an HTML artifact: a token
belongs to one file, so a dashboard made of `index.html` + `app.js` could not load its own
`./app.js` by relative path, and the bytes would come from `firebasestorage.googleapis.com` with
none of the headers above. So one small function serves the files:

```
viewer opens my.alldone.app/projects/P/artifacts/A
   │  reads the artifact doc (firestore.rules decide, exactly like a note read)
   │  builds the address from projectId, artifactId, serveSecret
   ▼
https://alldone-artifacts.web.app/a/P/A/<serveSecret>/index.html          (iframe src)
   │  Hosting rewrite ** → serveArtifact (onRequest, europe-west1)
   │  load the artifact doc (cached ≤60s) → compare serveSecret (constant time)
   │  stream the current version's file from Storage via the Admin SDK
   ▼
headers: CSP sandbox, X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer,
         Cache-Control: private, max-age=60
```

`…/{serveSecret}/~{versionId}/index.html` addresses one fixed version (immutable, cacheable for
long). Because the secret is a path segment, relative links inside a bundle resolve under it and
no cookie is involved. A cookie on the artifact site would be a third-party cookie inside the
app's iframe, which browsers increasingly block. `no-referrer` keeps the secret from leaking to
sites the artifact links to. A rotation takes effect within the 60-second cache window.

Artifact bytes carry no download token, and the `artifacts/` prefix must deny direct client reads
in the **production storage rules**. `firebase.json` deploys no storage rules; the live rules are
console-managed and must be audited in Phase 0.

Limits for Phase 1: 25 MB per file, 100 MB / 500 files per bundle, counted into the existing
`updateQuotaTraffic` quota.

## 5. UI

**List** (`components/ArtifactsView/`): per project and All projects, Followed / All toggle, sorted
by `lastEditionDate` desc. Row = kind icon, title, creator avatar (person or assistant), "edited
2h ago", size, lock icon when private. Filter chips by kind and by source. Drop zone over the whole
list (reuse `AttachmentDropZone`, capture phase — see AT-2441 in `CLAUDE.md`), plus an "Add
artifact" button.

**ArtifactDetailedView** (follows the `[Entity]DetailedView` pattern):

- **Preview** (default tab) — full-height sandboxed iframe; "Open full screen" opens the
  artifact URL alone; version picker in the header.
- **Properties** — title, description, privacy, owner, source + link to the originating object,
  versions with restore, download, delete, move to project.
- **Chat** — the object's own assistant thread. This is the core interaction: "make the bars blue",
  "add last month" → the assistant writes a new version → the preview reloads. Same loop as
  iterating with Claude on an artifact, inside the project's context.
- **Backlinks**, **Updates** — as for notes.

**URLs** (`URLSystem/Artifacts/`):

| Path                                                | Screen                      |
| --------------------------------------------------- | --------------------------- |
| `/projects/artifacts/followed` · `/all`             | All projects list           |
| `/projects/{projectId}/user/{userId}/artifacts/all` | Project list                |
| `/projects/{projectId}/artifacts/{artifactId}`      | Detailed view, Preview      |
| `…/{artifactId}/properties` · `/chat` · `/updates`  | Other DV tabs               |
| `…/{artifactId}/view`                               | Full screen, minimal chrome |

The app URL is the one to share: it requires sign-in and project access, exactly like a note
link. The raw `alldone-artifacts.web.app/a/…` address is what "Open full screen" opens. It stays
fixed until the secret is rotated and works without sign-in, like a note attachment link.

Offline: the list renders from the Firestore cache; the preview is an online-only surface and must
fail fast with the offline message (`isBrowserOffline()`), not spin.

## 6. Assistants, VM runs, MCP

- **Assistant tools** `create_artifact`, `update_artifact` (full content or a patch, plus
  `changeSummary`), `get_artifacts`, `read_artifact` (text of the current version). Wire every
  layer per the Assistant Tool Checklist in `CLAUDE.md` (schemas, `assistantHelper`, Tools Access,
  i18n). Default privacy: inherited from the thread's object (an artifact made in a private task
  is private) — decision 5.
- **VM jobs**: today `uploadArtifacts` in `vmJobRunner.js` turns `/home/user/output/` files into
  comment attachments with token URLs. Instead, deliverables become artifacts (a folder with an
  `index.html` becomes one `web` bundle), and the result comment links to them. The thread
  remembers the artifact id, so the next run in the same thread writes **version 2** of the same
  dashboard instead of a second copy. Agent prompt (`buildAgentPrompt`) gets one paragraph on this.
- **MCP**: the same tools on the Alldone MCP server, so Claude Code, Claude Desktop or Cursor can
  publish straight into a project ("publish this dashboard to project X").
- **Search**: a Typesense `artifacts` collection over title, description and extracted text.

## 7. Ideas beyond the brief

1. **Live dashboards without leaking data (the strongest one).** A dashboard that bakes numbers
   into its HTML shows everyone the data its _author_ could see. Instead: the artifact asks the
   **host app** for data over `postMessage` through a small bridge script (`/_alldone/bridge.js`,
   served by `serveArtifact`), e.g. `alldone.query('tasks', { done: true, since: '30d' })`. The
   app answers with the **viewer's own** client and permissions from a whitelisted, read-only
   query set. Every viewer sees their own correct numbers, the dashboard is always current, and
   the artifact contains no data at all. Data-bound artifacts get a strict CSP (`connect-src
'none'`, `img-src 'self' data: blob:`, `form-action 'none'`, no popups) so data handed to them
   cannot be sent anywhere. Opened outside Alldone the bridge is absent and the page says so.
2. **Sharing with people outside the project** (a client status dashboard, a report). The raw
   address already works without sign-in (§4), so this is a UI decision, not new infrastructure:
   a "Copy link for people outside the project" action with a clear warning, next to "Reset
   link". A data-bound artifact (idea 1) shows no data there, because the bridge only exists
   inside Alldone.
3. **Artifacts as deliverables.** A task or goal can name its result artifact ("Ergebnis"); an AI
   workflow step that produces one attaches it to the task it moves on, so the next reviewer
   reviews the artifact, not a chat message about it.
4. **Embed in notes**: `#artifact` links with backlinks like note links, and a live preview card as
   a note embed (must use `renderEmbedContent` / `reactEmbedBlot`, never `ReactDOM.render` on a
   blot node — AT-2454).
5. **Scheduled refresh**: a recurring assistant task that regenerates a report artifact every
   Monday — works with existing recurring tasks once `update_artifact` exists.
6. **Wiki citations**: the project wiki could cite artifacts as sources (only public ones, same
   filter as `isVisibleToWholeProject`).

## 9. Decisions (2026-10-24)

1. **Name: Artefakte.** UI strings: _Artifacts_ (en), _Artefakte_ (de), _Artefactos_ (es).
2. **The per-project Chats item stays in the sidebar.** The top-right button only opens All

3. **Updated 2026-10-25, AT-2828:** all project uploads, including existing ones, appear as links
   to their original readable sources. No automatic copies, independent access or public shares.
   "Show in artifacts" replaces the chip's copy action. VM deliverables remain full artifacts.
   See the linked-upload implementation notes below (supersedes the original explicit-promotion decision).
4. **Sharing outside the project comes in Phase 3.** The MVP offers "Open full screen" and "Reset
   link"; the raw link works without sign-in from day one, but the UI does not advertise it.
5. **AI-created artifacts inherit the privacy of the thread's object.** An artifact made in a
   private task is private.
6. **Domain: `alldone-artifacts.web.app`** (and a staging counterpart). Phase 1 starts on the
   function's own `cloudfunctions.net` address instead, see §10. A dedicated domain
   (`alldoneusercontent.com`, per-artifact subdomains) is reconsidered with sharing outside the
   project or for branding.

## 10. Implementation status

Built and tested on the branch:

- **Backend** (`functions/Artifacts/`): the shared model, `commitArtifactVersion`,
  `restoreArtifactVersion`, `resetArtifactLink`, `serveArtifact`, the update trigger (access
  projection + secret rotation on lost readers) and the delete trigger (versions and stored files).
  Rules for `artifactItems/{projectId}/artifacts/{id}` and its `versions`; the collection is in the
  access-projection sync.
- **Web**: the Artefakte tab in place of Chats (Chats stays in the sidebar and behind the top bar's
  button), a sidebar entry, list per project and for All projects, upload by button or drag and drop,
  the artifact opened in place with live preview, title, description, privacy, versions with restore,
  "Open full screen", "Reset link" and delete. URLs `/projects/{projectId}/artifacts[/{id}]` and
  `/projects/artifacts/all|followed`. Strings in en/de/es.
- **Tests**: function suites, the `project artifacts` block of the rules emulator suite, web suites,
  and `browser-tests/artifacts` (19 checks in real Chromium, mutation-checked).

Where Phase 1 deviates from the plan above, and why:

1. **Served from the function's own address, not `alldone-artifacts.web.app`.** A second Hosting
   site needs `firebase.json` to become a multi-site array with deploy targets, and from then on
   every `firebase deploy --only hosting` would fail until the site exists in the Firebase console
   of both projects. `https://europe-west1-<project>.cloudfunctions.net/serveArtifact` is just as
   separate from the app's origin. Switching later is one line (`getArtifactServeBaseUrl`) plus the
   Hosting site and a rewrite, never on an alldone.app host.
2. **Uploads go through the callable as base64, capped at 20 MB per upload.** Storage rules are
   console-managed and not in the repo, so a client upload to a staging path would depend on rules
   nobody here can see. The plan's 25 MB per file / 100 MB per bundle needs a signed-URL upload later.
3. **The artifact opens in place in the root view** (like a wiki page), not in a separate
   `ArtifactDetailedView` route. The object chat and the Updates tab move to Phase 2, where the chat
   becomes the place to iterate with an assistant.
4. **Every dropped file becomes its own artifact.** Multi-file artifacts are already supported by the
   model and by `serveArtifact`; they arrive through assistants and VM runs in Phase 2.
5. **The list opens on All, not Followed.** There is no way to follow an artifact yet, so Followed
   would only ever show the member's own uploads.

Phase 2, started:

- **Assistant tools** `get_artifacts`, `read_artifact`, `create_artifact`, `update_artifact` behind
  one Tools Access key (`artifacts`, on by default for new assistants; existing ones through
  `migration/enableArtifactToolForAssistants.js`), also on the Alldone MCP server. Updates send only
  what changed (exact text edits, whole files, removals) and keep every other file; a version written
  meanwhile makes the update fail instead of being overwritten. Privacy is inherited from the thread
  (decision 5). Assistants hand out the in-app link, never the serve link.
- **VM outputs as artifacts**, in addition to the chat attachments (not instead of them, so WhatsApp
  delivery and the assistant's read-side stay as they are): a folder with an `index.html` becomes one
  web bundle, other files their own artifact, and the next run in the same thread writes a new
  version of the same artifact. The links are added under the VM's answer.
- **"Change with assistant"** on an artifact: describe the change, and a chat with the project's
  assistant starts that names the artifact; the assistant reads it and saves a new version. Like the
  wiki's correction form it reuses `createBotQuickTopic` instead of a chat on the artifact itself, and
  it says so when the assistant does not have the artifact tools enabled. The detail also shows
  where an artifact came from (uploaded, assistant, VM run).
- **"Save as artifact" on chat attachments**: a small icon in the file chip of a chat message or
  comment copies the file into a new **private** artifact of the person saving it (the conversation
  may be readable by fewer people than the project); afterwards the icon opens it. The server only
  copies from this project's own bucket, from the attachment folders, and only when the URL carries
  the file's own download token. The same action sits on a file chip inside a note (only for files
  uploaded into the note; a comment draft's chip has none), with the note's project resolved from
  the editor registry.
- **A chat on the artifact itself** ("voll integriert"): artifacts are a chat object type like notes
  and skills (`chatComments/{p}/artifacts/{id}`), with followers, the assistant picker, unread
  state and the comment popup header. The detail switches between Artifact, Chat and Updates
  (`/projects/{p}/artifacts/{id}[/chat|/updates]`). "Change with assistant" now posts into that
  chat instead of starting a separate topic, so the change request and the new version sit next to
  each other.
- **Updates**: a history per artifact (`…/artifacts/{id}/history`, written only by Cloud Functions):
  creation and every version with the assistant that saved it, restores, link resets, the
  automatic link renewal when someone loses access, renames, description and privacy changes, and
  live data switched on or off.
- **Search**: a Typesense `artifacts` collection over title, description and the text of the entry
  file, with the same `projectId` + `isPublicFor` access fields as notes, as a sixth tab of the
  global search (its own request, because Typesense allows eight searches per request).
- **Backlinks**: an artifact URL in a task or note becomes a named link chip with a rename/open
  popup, and is stored as `linkedParentArtifactsIds`; the access projection turns that into
  per-reader backlink tokens, so the artifact lists "Linked from" without showing private matches.

Phase 3:

- **Sharing outside the project**: "Copy link" (the in-app address) and "Share outside the project",
  which explains what the serve address means before copying it.
- **Deliverables**: an artifact made in a task's or goal's thread is that object's result
  (server-owned `parentObject`) and is listed under the description as "Results".
- **Note embeds**: a link to an artifact in a note can be switched to a live preview card and back
  (its own quill embed, mounted through `renderEmbedContent`). The card reads the artifact with the
  viewer's access and says so when it is not available.
- **Live data bridge** (§7 idea 1, `functions/Artifacts/artifactDataBridge.js`): the owner switches
  "Live project data" on for a web artifact; the page loads `_alldone/bridge.js` and asks for the
  project, members, goals and open or done tasks. Three deviations from the sketch above, each for
  a reason found while building it:
    1. **The locked-down policy follows the address, not the document.** The app frames such a page at
       `?alldone-bridge=1`; serveArtifact answers that address with `sandbox allow-scripts`, no network
       requests, forms, popups or frames, and scripts only from the page and three CDNs. A cached
       response from before the switch therefore can never be the one that receives data.
    2. **Only project-shared objects are handed over**, never private items, not even the viewer's
       own — because two channels remain that no page policy closes (navigating the frame with data in
       the address, WebRTC/DNS prefetching), so the worst case is that a page leaks what every project
       member can see anyway.
    3. **A handshake, not a load counter.** A document says hello once and gets a session token; a
       second hello ends the conversation. Counting `load` events alone answered a page the frame had
       navigated to, because a new document's scripts run before its `load` event —
       `browser-tests/artifacts/bridge.js` found that (and proves the rest against a control page that
       can reach the "attacker").
       Assistants set it with `liveData` on `create_artifact` / `update_artifact`.

## Linked uploads (AT-2828, 2026-10-25)

The All list combines full artifacts with a read-time view of original uploads
(`utils/backends/Artifacts/linkedUploads.js`). It reads authorized task, note, goal, contact,
skill, topic, artifact and OKR documents, their comment threads, plus project-user and assistant
threads. Historical note bodies are decoded from their existing Yjs Storage content; no production
backfill, new collection, index or rules deployment is required. Profile pictures, assistant-skill
packages, unfinished composer drafts and unreferenced Storage objects are not project deliverables.

Every object query uses `readerIds`; comments use the original parent's rules. Aggregation is
member-only, including in shared projects. The current `isPublicFor` is checked again to remove
revoked sources while reader projections catch up. Rows open the source editor/thread; they expose
neither a Storage download capability nor a `serveArtifact` address, sharing control, version or
separate privacy setting. Source removal, comment edits, listener permission errors and project
membership loss clear the affected rows. Cancelled/in-flight note reads cannot repopulate them.

A stored path identifies one file, independently of display names or download-token rotations.
Several readable sources contribute one row; removing one source preserves the remaining links.
Existing independently copied artifacts remain independent: historical copies have no reliable
origin identity, so matching only by filename would hide unrelated files. VM-generated full
artifacts also remain distinct from their legacy chat-attachment copies.

The projection runs only while the All artifacts list is mounted. Followed still describes full
artifacts, which have their own followers. Existing uploads are not newly indexed in global
artifact search. It reads source documents and comment collections plus saved note bodies, so
large projects incur additional reads; note downloads are limited to four concurrently. No file
bytes are copied. A successful local note upload (including offline catch-up) updates only an
`uploadsRevision` marker after Storage completion so the list can refresh after the earlier
metadata write. Collaborator-only durability saves retain their content-only contract.
